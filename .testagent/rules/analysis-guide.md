# 测试分析方法指南

本文件是测试规格 md **前段（分析过程）**的方法论与参考资料。`test-spec-analysis` skill 生成前段时参照本文件，指导"怎么分析、分析里写什么"。

两条边界请注意：
- 本文件**只产定性分析结论**，不在分析过程里编排 TS 编号或 TS 清单。最终写入平台的普通 TS 清单一律按 [ts-split.md](ts-split.md) 的拆分方式与命名，填入 md **后段**的「平台写入数据」固定章节。
- TR 复用平台已有对象，以 `tr_info.json` 及其直接关联需求全集为准；本文件不创建、重命名或拆分 TR。

---

## 一、测试设计策略

### 特性风险分析（RBT）

**风险矩阵：**

```
            失效影响
            L    M    H
失效概率 L  L    M    M
        M  M    M    H
        H  H    H    H
```

**风险等级判定标准：**

| 失效概率 | 失效影响 | 风险等级 | 测试策略 |
|----------|----------|----------|----------|
| H | H | 高 | 加强测试，覆盖所有场景 |
| H | M | 高 | 加强测试，重点关注功能 |
| H | L | 中 | 关注功能测试 |
| M | H | 高 | 加强测试，重点关注功能 |
| M | M | 中 | 标准测试流程 |
| M | L | 中 | 关注功能测试 |
| L | H | 中 | 关注功能测试 |
| L | M | 低 | 基础测试覆盖 |
| L | L | 低 | 基础测试覆盖 |

**失效概率评估因素**：使用频率、进度压力、新功能占比、复杂程度、开发团队经验、异地开发情况、技术新颖性。

**失效影响评估因素**：对系统业务的影响程度、对客户体验的影响、对数据完整性的影响、对安全性的影响。

### 分层测试策略

**分层协同关系：**
1. **解决方案和产品分层**：验证端到端解决方案完整性
2. **产品和平台分层**：平台能力与产品特性解耦验证
3. **与周边网元/部件分层**：接口和交互验证
4. **SDV 和 SIT 分层**：明确分工，避免重复和遗漏

**分层测试输出**：各层测试的责任边界、测试准入准出标准、测试资产复用策略。

### 底层硬件/组网差异

- **硬件类型**：E9000、E9000H、RH2288、其他型号
- **组网类型**：EVS、OVS、SRIOV、SRIOV-Bonding、软SDN、硬SDN

### 网元形态差异

多网元类型测试覆盖策略：网元类型定义、各类型网元的测试重点、网元间交互测试场景。

## 二、已有 TR 的需求追溯分析

完整读取当前 TR 的直接关联需求和全部 SR 规格，建立“SR 测试内容 → 当前 TR 直接关联需求”的追溯关系。不得假定一个 IR 只能有一个 TR，也不得创建或重命名 TR。

### TR 分析输出要求

1. 覆盖当前 TR 范围内全部 SR（及其 US/AR）测试内容。
2. TR 元数据直接复用 tr_info.json；平台 requirement_ids 仅使用当前 TR 的直接关联需求编号。
3. 明确可测试性、来源覆盖和冲突影响，将分析结论归入 test-spec-analysis 规定的固定章节，不以追溯表替代前段分析。

## 三、测试场景分析（TS）：五维定性分析

对 TR 内整合的每项 SR 测试内容，依次从 5 个维度做**定性**分析，结论写入前段。**本章不编排 TS 编号、不产 TS 清单表**；最终 TS 条目按 [ts-split.md](ts-split.md) 落入后段固定章节（见本章末"与后段 TS 的衔接"）。

### 1. 场景分析

**目标**：根据系统设计中的业务处理流程，识别当前 TR 对应的业务功能场景。站在 E2E 不同客户角度分析端到端集成部署、组网场景等，包括云化部署、云化更新改造、云化组网等场景。

**输入**：系统设计文档、产品全量场景库。

**分析方法**：
1. 针对系统设计采用 IBO 分析法（Input-Behavior-Output）
2. 与产品全量场景库交互分析：
   - 基于 SIR(SSR)/IR 覆盖需求对应关联的 Scenario 场景
   - 其他全量 Scenario 场景交互

### 2. 测试类型分析

**目标**：分析被测需求的 DFX 场景，识别涉及的测试类型与关注点。

**输入**：测试类型清单。**方法**：被测需求与测试类型交互分析。

| 测试类型 | 是否涉及 | 分析说明 |
|----------|----------|----------|
| 功能性 |  |  |
| 性能 |  |  |
| 可靠性 |  |  |
| 易用性 |  |  |
| 安全性 |  |  |
| 可服务性 |  |  |
| AI测试 |  |  |
| 功能安全 |  |  |
| 兼容性 |  |  |
| 可测试性 |  |  |

### 3. 特性交互分析

**目标**：将被测对象与特性树高层节点交互分析，识别有交互场景的特性，得出特性交互测试场景。**输入**：特性树高层节点树。**方法**：交互分析。

### 4. 功能交互分析

**目标**：将被测对象与功能树高层节点交互分析，识别有交互场景的功能，得出功能交互测试场景。**输入**：全量功能库功能域（FUND）。**方法**：交互分析。

### 5. 设计约束分析

**目标**：针对设计约束逐条分析其在商用场景下是否合理、是否存在突破可能；若存在，需验证约束突破时商用特性不受影响。

**方法**：
1. 逐条分析设计约束的商用合理性
2. 识别可能突破约束的场景
3. 设计验证用例确保约束突破时商用特性不受影响

### IBO 分析法说明

- **Input（输入）**：业务操作的入口数据、触发条件
- **Behavior（行为）**：系统处理逻辑、业务流程
- **Output（输出）**：业务处理结果、响应数据

### 场景库交互分析

1. **基于需求关联的场景**：根据 SIR(SSR)/IR 中覆盖需求对应的 Scenario
2. **全量场景交叉**：与其他全量 Scenario 交叉分析，发现潜在交互场景

### 与后段 TS 的衔接

五维分析产出的是**定性结论**（每个 SR/场景测什么、关注点在哪），写在前段供评审。它**不直接生成 TS 清单**。最终 TS 按 ts-split.md 落入 md 后段固定表：

- **平台 DFX TS**：复用 platform_ts.json 中已有条目，按真实 platform_ts_id 生成独立规格；不进入普通 TS 清单，不新建 DFX TS。
- **普通 TS**：按 ts-split.md 的 scene/function/feature/constraint 四类定义及覆盖原则拆分，不再使用 per_sr/per_scenario 开关。
- 最终 Markdown 的固定标题和顺序以 test-spec-analysis 为准：前段分析、DFX 规格、末尾平台写入数据。方法指南中的编号标题不直接替代输出标题。
