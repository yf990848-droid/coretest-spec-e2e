# 需求文档解析器

本 skill 解析分层需求跟踪文档（通常为 .docx），提取结构化信息，并按 SR 维度拆分为独立产物文件。

## 文档结构概述

需求文档采用多级需求层次。

### 需求层级

**第 0 层 - 初始需求 (IR)**
- 客户或市场的初始需求
- 格式：IR###########
- 跟踪需求的来源与起点

**第 1 层 - 系统需求 (SR)**
- 由 IR 分解而来
- 格式：SR###########
- 包含功能描述、约束、规格说明
- 涵盖"利益相关方""需求描述""约束""规格""非功能需求"

**第 2 层 - 用户故事 (US)**
- SR 分配至具体组件或团队
- 格式：US###########
- 包含"输入""处理""输出"

需求前缀与常见模块缩写见 [references/domain-knowledge.md](references/domain-knowledge.md)。

## 产物形态

本 skill 产出 `sr_specs/` 目录：每个 SR 一份独立 md 文件，外加一份汇总头文件 `_index.md`（承载 IR 信息及无法归属到单个 SR 的横切信息）。

## 工作流程

按第 0 步至第 7 步处理。执行各步骤时须使用 `todowrite` 工具创建并跟踪任务，每步完成后更新状态为 `completed` 并输出进度信息。

### 第 0 步：读取辅助输入（如存在）

**目的**：接收上游 spec-extractor 的两份辅助输入，作为交叉校验与按 SR 分摊的素材。

**动作**：
- 检查 `<output_dir>` 下是否存在 `系统需求.md` 与 `功能设计.md`
- 存在则用 Read 工具读取并缓存为辅助上下文
- 不存在则跳过本步，不阻塞后续流程

**判断**：
- 两份均存在 → 读取并进入第 1 步
- 任一不存在 → 输出提示后继续，进入第 1 步（分摊步骤对应素材标注"辅助输入缺失"）
- 存在但读取失败 → 警告并跳过该文件，继续

**辅助输入用途**：
1. **交叉校验**：核对自 .docx 提取的 IR/SR/US 层次与辅助输入是否一致
2. **补充含糊字段**：当 .docx 某字段（如 ID、验收标准）描述含糊而辅助输入明确时，以辅助输入为准
3. **分摊素材**：第 6 步拆分时，自 `系统需求.md` 取功能行(F)、自 `功能设计.md` 取接口段，分摊进对应 SR 文件
4. **不引入新需求**：辅助输入仅用于校验与补充含糊字段，不得引入 .docx 中没有的需求项。.docx 为唯一权威来源

### 第 1 步：获取文档内容

用 pandoc 将文档转换为 markdown：

```
pandoc <输入文件路径> -o <输出文件路径> -t gfm
```

读取转换后的 markdown 内容。

### 第 2 步：文档分析

检查文档以了解：
- 需求领域
- 现有需求类型 (IR / SR / US)
- 层次深度与结构
- 特定领域术语

### 第 3 步：提取层次结构

重构需求层次：
- 依"级别"列识别需求类型
- 识别 IR → SR → US 的跟踪链

示例层次：

```
IR20251125001288 (初始需求)
├── SR20260207294867 (系统需求1)
|   ├── US20260207294994 (用户故事1)
└── SR20260206265033 (系统需求2)
    ├── US20260206265149 (用户故事2)
```

### 第 4 步：提取关键信息

逐一提取各需求层级信息，存在多个 SR 时确保无遗漏。

**辅助输入交叉校验**（仅当第 0 步读取到辅助输入时启用）：
- 提取 IR/SR/US 层次时，与辅助输入需求清单交叉对比，验证有无遗漏
- 提取 SR 的"实现接口设计"时，参考 `功能设计.md` 接口清单补充
- 提取 SR 的"规格"与"约束"时，参考 `系统需求.md` 验收标准
- 交叉校验不得引入 .docx 中没有的需求项

**IR 提取字段**：
- 来源（客户或市场驱动因素）
- 问题描述
- 目标客户/市场
- 业务价值
- 系统上下文
- 系统需求列表
- 分配需求列表

**SR 提取字段**：
- 利益相关方
- 需求描述
- 约束（如依赖其他特性或软参，须重点提取）
- 规格（量化规格说明）
- 非功能需求（性能、可靠性、可维护性、可测试性）
- 实现思路
- 实现设计（介绍 / 输入 / 处理 / 输出，处理含表格时须提取表格内容）
- 实现接口设计
- OM设计
- 外部接口设计
- 资料设计

### 第 5 步：横切信息归集

归集以下横切信息，供第 6 步按确定性映射表分摊：
- 关键功能清单
- 约束与依赖清单
- 非功能需求（性能/可靠性/可维护性/可测试性）
- 需求类别（业务功能、运维配置、License、性能指标、安全等）
- 利益相关者与模块归属

### 第 6 步：按 SR 拆分与确定性分摊

**目的**：将第 4、5 步提取的信息按 SR 维度重组，产出 `sr_specs/` 下每个 SR 一份独立文件及一份汇总头文件。

**拆分原则**：
- 每识别到 1 个 SR，产 1 份 `<output_dir>/sr_specs/SR<编号>.md`
- 横切信息（关键功能 / 约束 / 非功能需求 / 接口段）按下列确定性规则挂至对应 SR，不依赖临时判断
- 确定性规则未覆盖、归属不明的横切项，统一收入 `_index.md` 的"未分摊横切信息"段，不强行归入某 SR

**确定性分摊规则**（按字段关键字匹配，逐条将横切项映射至 SR）：

1. **关键功能 → SR**：按关键功能描述中出现的实体（数据表 / 动作组 / 配置命令 / 性能指标 / License / 软参等），匹配"实现思路 / OM设计 / 约束"字段中出现同一实体的 SR
2. **约束 → SR**：约束中出现的实体，按与关键功能相同的实体匹配规则挂至同一 SR
3. **依赖项 → SR**：作为多个 SR 共同前置的核心触发类依赖，挂至相关的各 SR 各一份（重复无害）
4. **非功能需求 → SR**：性能/可靠性/可测试性指标挂至性能可靠性验证类 SR；可维护性（维测/话统/审计）挂至维测能力类 SR
5. **接口段（自功能设计.md）→ SR**：按接口名或 MML 命令名，匹配 SR"实现接口设计 / 外部接口设计 / OM设计"字段中出现的同名接口；匹配则完整附入，该字段无接口则标注"本 SR 无接口设计"
6. **利益相关者整段**：不分摊、不写入任何 SR。模块归属由各 SR 的关联 US 列表"系统元素"列承载，`_index.md` 中以一句话注明

产物结构（SR 文件结构、`_index.md` 结构）见 [references/output-templates.md](references/output-templates.md)。

**判断**：
- 每个识别到的 SR 均产出对应文件 → 进入第 7 步
- 某 SR 信息严重缺失（无主体、无 F 行、无 US）→ 仍产出文件，文件顶部标注"本 SR 提取信息稀薄，请人工复核"
- "未分摊横切信息"条目较多 → 在 `_index.md` 中明确，提示人工复核

### 第 7 步：生成摘要

向调用方汇总：
- IR 编号与 SR 总数
- 产出的 SR 文件清单（路径）
- `_index.md` 路径
- "未分摊横切信息"条目数

## 输出文件

所有产物写入 `<output_dir>/sr_specs/`：

```
<output_dir>/sr_specs/
├── _index.md            （IR 信息 + SR 清单 + 分摊审计 + 未分摊横切信息）
├── SR<编号1>.md
├── SR<编号2>.md
└── ...                  （每个 SR 一份）
```

文件结构见 [references/output-templates.md](references/output-templates.md)。

## 边缘情况

**特殊文件类型**：文档可能含指向外部需求管理工具的超链接、嵌入图片或图表、筛选/排序状态。

**缺失或不一致的数据**：
- 行信息不完整、层次结构有缺口、编码引用不一致、存在非标准列名
- IR 头部声明的 US 数量与 US 表实际行数不一致时，以 US 表实际行数为准，并在 `_index.md` 注明差异

## 注意事项

- 分摊须按确定性映射规则执行，不做临时归属判断，避免归属漂移
- 产物语言与原文档一致（中文 .docx 产出中文 SR 文件）
- 不读写 `<output_dir>` 以外的文件
