# Spec Extractor - 需求文档规格抽取助手

## 1. 功能定位

该 SKILL 用于从需求 Word 文档(.docx)中抽取信息,**重新组织** 为两份固定模板的 markdown 文件:

- `系统需求.md` — SRS/PRD 精简可测试版,7 节固定结构
- `功能设计.md` — 接口设计 Spec,OpenAPI 风格

本 SKILL 是 `/coretest-explore` 命令链的 Step 2a。

## 2. 输入要求

调用方需提供:

- `<docx_path>`:Word 文档(.docx)的本地绝对路径
- `<output_dir>`:输出目录(通常是 `corespec/changes/test-<需求id>-<name>/`)

可选辅助信息(命令传入,用于变更记录):

- `<source_id>`:来源标识(需求 ID 如 IR20251125001261,或 .docx 文件名)
- `<author>`:作者标识(默认 `c00959281(via spec-extractor)`)

## 3. 执行模式

**重要说明**:本 SKILL 采用 **AI 自主重组** 的执行模式,不是机械字段映射。

工作流分两个明确阶段:
- **阶段 A**:用 pandoc 把 .docx 转为 markdown(机械步骤,通过 Bash 工具调用)
- **阶段 B**:AI 读全文,按两个模板重新组织内容,产出两个独立 md 文件(AI 推理步骤,使用 Write 工具)

阶段 B 是核心,AI 必须:
- 通读全文后再开始组织,不要边读边写
- 原文有什么填什么,原文未提及的章节 **诚实说明**,不要编造、不要笼统占位
- 不要补充原文没有的信息,只能重组、提炼、归类

**必须使用 todowrite 工具** 创建并跟踪 6 个子步骤,每步完成后更新状态为 `completed`,并输出进度信息。

## 4. 工作流程

### 第 1 步:验证输入

**动作**:
- 检查 `<docx_path>` 文件存在且后缀是 `.docx`
- 检查 `<output_dir>` 存在,不存在则创建

**判断**:
- 文件不存在 → 报错并退出
- 后缀不是 .docx → 报错并退出
- 输出目录不可写 → 报错并退出
- 全部通过 → 进入第 2 步

### 第 2 步:pandoc 转换

**动作**:用 pandoc 将 .docx 转为 markdown,中间产物落到 `<output_dir>/.tmp_docx.md`

**调用方式**(通过 Bash 工具):

```bash
pandoc "<docx_path>" -o "<output_dir>/.tmp_docx.md" -t gfm
```

**判断**:
- pandoc 未安装 → 报错并提示安装命令:
  - Windows: `winget install --id JohnMacFarlane.Pandoc` 或下载 https://pandoc.org/installing.html 的 msi
  - Linux: `apt install pandoc`
  - macOS: `brew install pandoc`
- 转换失败(非 0 退出码) → 报错,展示 pandoc stderr 输出
- 转换成功 → 进入第 3 步

### 第 3 步:通读全文

**动作**:用 Read 工具读取 `<output_dir>/.tmp_docx.md` 的完整内容,AI 通读理解全文。

**重点关注**:
- 文档标题、版本号、变更记录(用于填充"文档信息"块)
- 系统需求 / 功能列表 / 验收标准 / 非功能需求 等章节(系统需求.md 用)
- 接口定义 / API 设计 / 输入输出格式 等章节(功能设计.md 用)
- 数据模型、约束、术语 等横切信息(分散填入两个模板)

**判断**:
- 文档为空或解析后只有少量内容(<200 字) → 警告但继续,后续大量章节会落到"诚实说明"分支
- 文档结构清晰 → 进入第 4 步

### 第 4 步:生成 系统需求.md

**动作**:AI 按 7 节固定模板组织内容,写到 `<output_dir>/系统需求.md`

**模板**(严格 7 节,顺序不可调整):

````markdown
# 系统需求规格说明书

## 0. 文档信息

- 文档名称:<从原文档标题提取,或填 "<需求名>系统需求规格说明书">
- 版本:V1.0
- 日期:<当天日期 YYYY-MM-DD>
- 作者:<author>
- 变更记录:

| 版本 | 日期 | 变更人 | 变更内容 |
|------|------|--------|----------|
| V1.0 | <当天日期> | <author> | 从 <source_id> 自动提取 |

## 1. 引言

### 1.1 目的
<从原文档提取系统目的,1-3 句话>

### 1.2 范围
<从原文档提取系统范围,包含什么、不包含什么>

### 1.3 目标用户
<从原文档提取目标用户群体>

### 1.4 术语
<从原文档提取专业术语和缩略语>

## 2. 总体描述

### 2.1 产品愿景
<从原文档提取产品愿景或定位>

### 2.2 运行环境
<从原文档提取运行环境约束,如操作系统、浏览器、网元形态>

### 2.3 设计约束
<从原文档提取设计约束和限制>

## 3. 功能需求

| ID | 功能名称 | 前置条件 | 输入 | 处理逻辑 | 输出/预期 | 验收标准 |
|----|---------|---------|------|---------|----------|---------|
| F001 | <功能 1 名称> | <前置> | <输入> | <处理> | <输出> | <验收> |
| F002 | <功能 2 名称> | ... | ... | ... | ... | ... |

## 4. 非功能需求

- 性能:<从原文档提取性能指标>
- 安全:<从原文档提取安全要求>
- 兼容性:<从原文档提取兼容性要求>
- 可用性:<从原文档提取可用性要求>

## 5. 接口需求

<简述接口列表,每条:接口名 + 方法 + 路径。详细接口设计见 功能设计.md>

- <接口 1 名称>:<METHOD> <PATH>
- <接口 2 名称>:<METHOD> <PATH>

## 6. 数据需求

<从原文档提取数据模型/表结构定义>

- <表/实体名>:<字段列表>

## 7. 验收标准

- 功能:<功能维度验收>
- 性能:<性能维度验收>
- 安全:<安全维度验收>
````

**章节缺失处理**:

原 .docx 未覆盖某节时,**诚实说明** 缺失的是哪一节,用 blockquote 标记:

```markdown
## 6. 数据需求

> _本需求 .docx 未提及"数据需求"章节_
```

**严禁**:
- 编造 .docx 没有的内容
- 用笼统的"无"或"待补充"代替具体说明
- 把不属于本节的内容硬塞进来

**判断**:
- 至少 3 节(引言/总体/功能需求)有实际内容 → 正常完成
- 7 节里超过 4 节是诚实说明缺失 → 警告,但继续产出第 5 步

### 第 5 步:生成 功能设计.md

**动作**:AI 按接口设计 Spec(OpenAPI 风格)组织内容,写到 `<output_dir>/功能设计.md`

**模板**:

````markdown
# 功能设计 - 接口设计 Spec

## 文档信息

- 名称:<需求名>接口设计 Spec
- 版本:V1.0
- 基础地址:<从原文档提取,如 https://api.xxx.com/v1。若无则填 "本需求 .docx 未提及基础地址">
- 鉴权:<从原文档提取,如 JWT。若无则填 "本需求 .docx 未提及鉴权方式">

## 接口列表

### 接口 1:<接口名称>

- 接口路径:<PATH>
- 请求方式:<METHOD>
- 接口描述:<从原文档提取>
- 请求头:
  - Content-Type:<from doc>
  - <其他头部>
- 请求参数:

| 参数名 | 类型 | 必选 | 长度/范围 | 说明 | 枚举/示例 |
|--------|------|------|----------|------|-----------|
| <param1> | String | 是 | ... | ... | ... |

- 响应参数:

| 参数名 | 类型 | 说明 | 示例 |
|--------|------|------|------|
| code | Int | 状态码 | 200=成功 |
| msg | String | 提示信息 | ... |
| data | Object | 成功数据 | ... |

或响应示例(JSON):

```json
{
  "code": 200,
  "msg": "success",
  "data": { ... }
}
```

- 错误码:
  - 200:成功
  - 400:参数错误
  - <其他>

- 备注:<从原文档提取>

### 接口 2:...

(后续接口同样格式)
````

**接口缺失处理**:

原 .docx 未定义接口时,产出占位说明:

```markdown
## 接口列表

> _本需求 .docx 未提及具体接口设计_
>
> 若需补充,请手工编辑本文件或联系 SE/开发同事获取接口契约
```

**判断**:
- 至少抽到 1 个接口完整定义 → 正常完成
- 一个接口都没有 → 警告,产出占位说明后继续

### 第 6 步:清理与汇总

**动作**:
- 删除中间文件 `<output_dir>/.tmp_docx.md`
- 向调用方汇总:
  - 抽取到的功能需求数量
  - 抽取到的接口数量
  - 哪些章节是"诚实说明缺失"
  - 两个产物文件路径

**判断**:
- 全部 6 步通过 → SKILL 结束
- 任何步骤报警(章节缺失过多/0 接口) → 在汇总中明确标注,提示用户审阅产物质量

## 7. Guardrails

- **每个阶段执行后,AI 必须做出判断再决定下一步**(参照 core-explore Skill 的执行模式)
- **必须 todowrite 跟踪 6 个子步骤**,不允许跳过此跟踪机制
- **严禁补充原文没有的内容**,只能重组、提炼、归类
- **章节缺失必须诚实说明哪一节,不要笼统占位**
- **产物语言与原文档一致**(中文 .docx → 中文产物)
- **不读不写 `<output_dir>` 外的文件**,避免污染其他 change 目录

## 9. 常见错误与对策

| 错误现象 | 原因 | 对策 |
|---------|------|------|
| pandoc 命令找不到 | 未安装 | 按第 2 步提示安装 |
| 转换出的 md 是乱码 | .docx 编码异常或含图片为主 | 切回原文件用 Word 打开另存为 .docx,或手工补充内容 |
| 7 节里 5+ 节是诚实说明 | .docx 内容稀薄或不是规范的需求文档 | 警告用户检查 .docx 质量,或切回模式 A 手工补充 |
| 0 个接口被抽出 | .docx 是纯文字描述,无接口定义 | 产出占位说明,提示用户后续手工补 |
| 产物语言不一致(中英文混) | .docx 自身就混 | 不强行统一,产物保留原文语言混合状态 |
