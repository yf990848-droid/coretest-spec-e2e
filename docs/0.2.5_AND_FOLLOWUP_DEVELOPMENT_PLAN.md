# coretest-spec-e2e 0.2.5 及后续版本开发计划

> 制定时间：2026-09-15  
> 当前基线：`develop` 分支，扩展版本 `0.2.4`

## 1. 目标

本计划用于安排以下需求：

1. Init 获取设计阶段全量需求关联的特性和功能，供创建 TR 时使用；
2. 测试用例卡片适配公司新版本，支持按需上报字段和创建 IDE 工程；
3. DFX 测试设计准则由 AI 自主检索、匹配并生成 TP；
4. Explore 支持三种“需求到 TR”的分组方式；
5. Archive 适配全量在线文档，将过程文档写入对应章节；
6. 扩展包支持流程策略配置，并使 Explore 到 TP 的分组策略保持一致；
7. 完成 TS、TP 因子选择及归档关联。

需求中的优先级数字按以下方式理解：

| 优先级 | 含义 |
|---|---|
| 1 | 本月最高优先级 |
| 2 | 本月重要功能 |
| 3 | 大改动或可扩展性功能 |

实际开发顺序还要考虑依赖关系。建议先稳定因子、卡片和文档，再改变 TR 分组主流程。

## 3. 0.2.5：因子关联闭环

### 3.1 已验证内容

目前已经验证：

- scene TS 可以关联 TestFactor；
- function TS 可以关联 TestFactor；
- constraint TS 可以关联 TestFactor；
- DFX TS 可以关联 TestFactor；
- scene TS 可以关联 SceneFactor；
- TS TestFactor 重复写入返回 `created=0`，没有产生重复关系；
- SceneFactor 可以通过 CLI 查询，并在页面正常显示；
- TP 可以通过 CLI 的 `--relations` 参数创建。

### 3.2 剩余问题

#### TP 测试因子显示问题（已定位）

现场对照确认：`testFactorId` 使用图谱 `test_factor_id` UUID，传 TS 因子
关系数字 `id` 时页面不显示名称和编码。scene 双因子以及 function、constraint、
DFX TP 已通过手工 CLI 页面验证；扩展包端到端仍需回归。

#### Feature TS 未现场验证

Feature 与 function、constraint、DFX 一样只使用 TestFactor。若本月有可用 Feature TS，应补一次真实验证；没有测试对象时可先做契约测试，不阻断 `0.2.5`。

#### 当前规则存在错误映射

旧版 `.testagent/rules/tp-tc-design-logic.md` 将“功能交互设计”因子映射到
`sceneFactorNames`，与已确认规则不一致；develop 已改为显式因子 ID 计划。

正确规则是：

- scene TS 及其 TP 可以使用 SceneFactor 和 TestFactor；
- function、feature、constraint、DFX TS 及其 TP 只使用 TestFactor。

### 3.3 Design 阶段实现

Design 阶段只选择因子并保存本地计划，不写平台：

1. 先根据完整 TS 规格检索并选择 TS 因子；
2. 生成 TP 时，只能从当前 TS 已选因子中选择子集；
3. 每个已保留的 TS 因子至少被一个 TP 使用；
4. 未被任何 TP 使用的因子从 TS 计划中删除；
5. 图谱无匹配因子时保存空数组并继续；
6. scene TS 同时支持 SceneFactor 和 TestFactor；
7. 其他 TS 只保存 TestFactor。

默认数量限制：

| 范围 | 最大数量 |
|---|---:|
| 每个 TS 的全部因子 | 5 |
| 每个 TP 的全部因子 | 3 |

SceneFactor 与 TestFactor 合并计数，而不是分别计算。

建议为每个 TS 保存一份结构化因子计划，能够明确区分：

- TS 选中的 SceneFactor；
- TS 选中的 TestFactor；
- 各 TP 选中的 SceneFactor 子集；
- 各 TP 选中的 TestFactor 子集；
- 因子 ID、编码、名称、类型、来源及关联活动类型。

### 3.4 Archive 阶段实现

Archive 执行真实平台写入：

1. TS 创建或复用成功后，写入 TS 因子；
2. TP 创建时，通过 CLI `--relations` 原子关联 TP 因子；
3. TS 因子关联失败时记录失败，但不阻断 TP/TC 创建；
4. 保存每次 CLI 请求和原始响应；
5. 将因子关联状态写入 `archive_state.json`；
6. 重跑时复用已有关系，不重复创建；
7. `created=0` 且查询已存在时视为幂等成功；
8. `created=0` 且查询不存在时视为失败。

### 3.5 验收标准

| 测试对象 | 因子类型 | 验证要求 |
|---|---|---|
| scene TS | SceneFactor + TestFactor | 创建、查询、页面显示、重跑幂等 |
| scene TP | SceneFactor + TestFactor 子集 | 名称和编码正常显示 |
| function TP | TestFactor | 页面正常显示 |
| constraint TP | TestFactor | 页面正常显示 |
| DFX TP | TestFactor | 页面正常显示 |
| feature TP | TestFactor | 有对象时现场验证，否则契约测试 |
| 无匹配因子 | 空数组 | Design 和 Archive 正常继续 |
| 重复 Archive | 已有关联 | 不产生重复关系 |

`0.2.5` 发布门槛：以上主要路径通过，尤其是 TP TestFactor 名称和编码显示正常。
旧 TP 因子补录不在本版范围；历史 TP 只按已有对象状态复用。

## 4. 0.2.6：卡片与在线文档适配

### 4.1 新版测试用例卡片

先确认公司新版卡片的数据契约：

- 必填字段；
- 可选字段；
- 空值字段是不传，还是传空字符串；
- 字段按需上报的配置方式；
- IDE 工程创建的请求、响应和失败语义；
- 是否需要兼容旧版卡片。

实现建议：

1. 建立统一字段白名单；
2. 只发送用户或策略启用的可选字段；
3. 必填字段无论配置如何都必须发送；
4. IDE 工程创建结果写入卡片状态；
5. 保持现有 TS/TP/TC Markdown 和 JSON 产物兼容。

验收：

- 只有必填字段时能生成卡片；
- 每个可选字段可以独立开启和关闭；
- 未启用的字段不出现在请求中；
- IDE 工程创建成功和失败都能明确展示；
- 旧产物仍可生成新版卡片。

### 4.2 在线文档适配

当前 `0.2.4` 已具备：

- 设计任务7个叶子章节写入；
- TR 5个章节写入；
- TS 按类型写入对应章节；
- 文档状态单独保存；
- 单个文档节点失败不回滚对象。

因此先做新版差距分析，只补充：

- 公司新版在线文档的章节名称或层级变化；
- 尚未同步的过程文档；
- 文本、表格等展示格式；
- 在线评审需要的状态、标记或链接。

不重写完整 `document_sync.py`。验收时检查所有预期章节均可在线查看和评审。

## 5. 0.2.7：Init 全量关系与 DFX 准则

### 5.1 Init 获取全量功能和特性

当前 Init 已保存已有 TR 自身的：

- `relation_function`；
- `relation_feature`；
- `function_list`；
- `feature_list`。

新需求是在创建 TR 前，获取设计任务中全部需求关联的功能和特性。

建议新增任务级文件：

```text
.design_output/<design_task_id>/requirement_relations.json
```

建议结构：

```json
{
  "requirements": [],
  "function_numbers": [],
  "feature_numbers": [],
  "relations": [],
  "conflicts": []
}
```

执行步骤：

1. 获取设计任务的全量需求；
2. 查询每条需求关联的功能和特性；
3. 按编号去重；
4. 保存需求与功能/特性的来源关系；
5. 保存无法确认或冲突的数据；
6. 后续创建 TR 时读取该文件，不临时重新查询。

本版本先把“全量获取、去重、保存、校验”做稳定，不同时修改 Explore 的三种 TR 分组。

### 5.2 DFX 测试设计准则匹配

处理流程：

```text
DFX TS 完整规格
→ 检索测试设计准则候选
→ AI 判断适用性
→ 保留适用准则
→ 根据准则生成 TP
```

要求：

- AI 只能从检索到的准则候选中选择，不能凭空编造准则；
- 本地记录准则 ID、名称、适用 DFX 类型和匹配理由；
- 记录准则生成了哪些 TP；
- 无适用准则时保存空结果并继续；
- TP 的 `tpSourceType` 使用“测试类型交互设计—测试设计准则”；
- 不改变当前 DFX TS 的平台复用规则。

## 6. 0.3.0：Explore 三种 TR 分组

这项会改变当前“Init 获取已有 TR，Explore 只分析已有 TR”的核心契约，应单独开发和回归。

统一流程：

```text
全量需求
→ 用户选择分组方式
→ 生成 tr_plan.json
→ 用户确认
→ 创建或复用 TR
→ 每个 TR 独立进入 Explore
```

三种方式：

### 方式一：IR 与其全部 SR 分组

- 每个 IR 与该 IR 下的全部 SR 创建一个 TR；
- 不属于任何 IR 分组的独立 SR 单独创建 TR。

### 方式二：全部需求合并

- 将当前设计任务的全部需求合并为一个 TR；
- 适合规模较小、边界统一的需求集合。

### 方式三：用户在卡片手工分组

- 用户在全量测试设计卡片中完成 TR 分解；
- 点击继续后，扩展包读取并校验分组结果；
- 不由 AI 再次改变用户确认的分组。

三种方式都输出统一的 `tr_plan.json`。后续流程只读取该文件，不分别实现三套 Design 和 Archive 逻辑。

验收重点：

- 每个需求恰好属于一个 TR 分组；
- 不丢失需求，不重复分配；
- 功能和特性关系来自 Init 保存的全量关系文件；
- 用户确认前不创建 TR；
- 重跑不会重复创建已有 TR；
- 每个 TR 使用独立标准目录进入 Explore。

## 7. 0.3.1：策略配置化

在 `0.3.0` 分组流程稳定后，再增加统一配置入口。

建议配置：

```yaml
tr_grouping:
  mode: ir_with_all_sr

factor_selection:
  max_ts_factors: 5
  max_tp_factors: 3
  product_scope: UPCF

tp_grouping:
  align_with_explore: true

test_case_card:
  optional_fields: []
  create_ide_project: false
```

配置优先级：

```text
用户本次明确选择
> 项目配置
> 扩展包默认值
```

要求：

- 所有阶段读取同一份策略；
- 不在不同 Skill 中维护重复配置；
- Explore 确定的分组标识传递到 TS、TP；
- Design 不重新推断或改变 Explore 已确认的分组；
- 缺少配置时使用安全默认值并保持现有行为。

## 9. 开发原则

- 每个版本只解决一个相对独立的问题；
- 每次修改都保持 [TS、TP、TC Markdown 格式](./TS_TP_TC_MARKDOWN_CONTRACT.md) 和标准路径不变；
- Design 阶段只生成计划，Archive 阶段才写平台；
- 平台 DFX TS 始终复用，不重复创建；
- 不因为单个因子或文档节点失败而回滚已经成功的对象；
- 先通过确定性脚本生成和校验数据，再调用平台写入；
- 每个版本先完成本地验证，再修改主流程，最后执行平台回归；
- `develop` 验证完成后再合入 `main`。
